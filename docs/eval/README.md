# eval 报告示例

`sample-report.md` 是 `pnpm eval` 的一份真实输出（2026-08-29，qwen-plus + extract-v2）。

放在这里的目的是让人不用跑起来就能看到**评测长什么样**：错误怎么分型、
逐字段准确率怎么排、失败样本怎么留痕。

---

## ⚠️ 先读这一段，不然会误读

**这份报告里的 24 条样本全部是人工构造的合成对话，不是真实客户对话。**

合成对话的措辞比真人规整得多。真实微信对话里客户会说
「差不多三年吧，中间好像断过两个月还是三个月记不清了」，
合成样本不会有这种混乱程度。所以：

| 这些数字能用来做什么 | 不能用来做什么 |
|---|---|
| **回归测试** —— 改 prompt 后验证旧缺陷没被带回来 | 声称生产环境准确率 |
| 三个模型横向对比（同一批样本，条件一致） | 跟别的项目的 benchmark 比较 |
| 定回归门禁基线（掉出区间就是引入退化） | 对客户或雇主承诺效果 |

**99.7% 是「回归基线的稳定性」，不是「生产准确率」。**
真实对话上这个数字必然会掉，掉多少现在无法预估——
因为真实样本数量还不足以支撑统计意义上的结论。

`origin='real'` 目前为 0 条。要出可信的生产数字，需要积累真实对话并重新标注，
这件事排在欠账清单里（见主 README 第十一节）。

## 为什么单次报告的小数点后一位不可信

同模型、同样本、同 `temperature=0`，连跑三次的结果并不完全一致：

| 轮次 | 全字段 | 硬字段 | 幻觉率 |
|---|---|---|---|
| 第 1 次 | 99.7% | 100.0% | 0.3% |
| 第 2 次 | 100.0% | 100.0% | 0.0% |
| 第 3 次 | 99.7% | 100.0% | 0.3% |

99.7% 与 100.0% 的差别是**一次**字段判定翻转（359/360 对 360/360）。

所以正确的读法是「落在 99.8 ± 0.17 这个带宽内的一次采样」，
不是「这个模型的准确率是 99.7%」。
`temperature=0` 只降低随机性，不消除——服务端的采样、批处理、
浮点累加顺序都可能引入差异。

三轮里**硬字段零方差**（收入/社保/公积金/征信查询/负债/营业年限
全部 360/360），会抖的是非硬字段。这个分布对系统有利：
决定能不能推单的六个字段是稳的。

## 报告怎么读

**总览表不只看准确率。** 幻觉率单列，因为错误代价不对称——
幻觉（客户没说却编出数字）可能导致推错单，一次就毁中介信任；
漏抽只需人工补问一句。混成一个百分比等于把最贵的错误藏起来。

**逐字段表按准确率升序排，最差的在最前面。** 这个排序是刻意的：
只看总分会误判成「整体略差」，实际往往是一个字段的定义没说清。
主 README 第二节记了一个具体例子——某个模型 8 个错里 7 个集中在同一字段，
修 prompt 比换模型便宜得多。

**失败明细带样本考点。** 每条样本对应一个已知失效模式，
所以失败明细不只告诉你「错了」，还告诉你「哪个防线破了」。

## 自己跑

```bash
pnpm gold:seed               # 灌入 24 条基准样本
pnpm eval                    # 默认 qwen-plus
pnpm eval --model qwen-flash --limit 10
pnpm eval --no-save          # 不落库，调试用
```

需要 `BAILIAN_API_KEY`（会真实调用付费 API）。

完整报告输出到 `eval-reports/`，该目录**已 gitignore**——
真实客户对话进过那里，不能入库。本目录这一份是人工确认过、
只含合成样本的副本。
